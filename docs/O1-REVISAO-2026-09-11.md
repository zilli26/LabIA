## Achados para correção

### 1. P1 — Proteção local não autentica o operador nem valida Host

Arquivo: `lib/providers/local-provider-access.ts`, linhas 33–49; todas as rotas O1 dependem desse gate.

O gate confia em `request.url`, ignora o header Host e aceita Origin de qualquer porta loopback. Ausência de Origin também é aceita; não existe sessão ou token. Os testes de revisão demonstram acesso aceito com Host não local e com Origin `http://localhost:9999` para serviço em `localhost:3000`. Isso viola o contrato original de pareamento/autenticação local. A URL interna do Next não é prova da origem da conexão de rede.

Correção: listener exclusivamente loopback, Host permitido, igualdade de Origin incluindo protocolo/porta e autenticação do operador com token/sessão de pareamento. Cobrir requisições sem Origin, com headers forjados e de outra aplicação local; testar rotas, não apenas o predicado.

### 2. P1 — Acesso por ID ignora workspace e dono

Arquivo: `lib/db/provider-connections.ts`, linhas 54–71; `connection-service.ts`, linhas 296–303.

A listagem filtra workspace/ownerKey, mas get/update consultam apenas `id`; `requireOpenAIConnection` verifica somente o provider. Com ID de outra conexão, leitura e ações podem atuar em outro dono/workspace. A revisão reproduziu retorno de conexão com `another-workspace`/`another-owner` sem rejeição.

Correção: aplicar o escopo do operador/workspace em todas as consultas e mutações e derivá-lo no servidor. Incluir testes de leitura, status, cancelamento e logout entre donos/workspaces.

### 3. P1 — Migration não protege a tabela contra a Data API

Arquivo: `prisma/migrations/20260911090000_add_provider_connections/migration.sql`, linhas 1–43.

A migration cria tabela no schema padrão, mas não habilita RLS nem revoga acesso de `anon`/`authenticated`. No Supabase consultado, os default grants concedem acesso a tabelas novas para esses papéis. Aplicar a migration como está pode permitir leitura/alteração dos metadados da conexão pela Data API, contornando as rotas locais. Os tokens não estão nessa tabela; o problema é acesso e integridade dos registros, incluindo dono, estado e referência de credencial.

Correção: como O1 usa Prisma no servidor, habilitar RLS sem políticas públicas e revogar privilégios desnecessários, ou usar schema privado. Validar permissões no banco de desenvolvimento antes de aplicar. [Referência oficial](https://supabase.com/docs/guides/api/securing-your-api).

### 4. P1 — Desconectar pode deixar a sessão OpenAI ativa

Arquivo: `lib/providers/openai-codex/connection-service.ts`, linhas 214–245.

Depois de reiniciar o Next, o mapa de runtimes fica vazio, mas a sessão permanece no diretório dedicado. `disconnectOpenAIConnection` só chama logout quando já há runtime; caso contrário, marca DISCONNECTED sem remover a sessão. Além disso, ignora qualquer erro de logout. O teste de revisão confirmou retorno de sucesso sem chamada de logout. Uma reconexão posterior pode recuperar a sessão supostamente desconectada.

Correção: recuperar o executor dedicado para efetuar logout mesmo após restart e só confirmar desconexão após sua conclusão. Em caso de erro, preservar estado de falha explícito. Testar restart, logout que falha e reconexão depois de logout.

### 5. P2 — Correlação de login existe no cliente, mas não é usada pelo serviço

Arquivo: `lib/providers/openai-codex/connection-service.ts`, linhas 142–161; `app-server-client.ts`, método `waitForLogin`.

O serviço não chama `waitForLogin`. Status usa somente `account/read(false)` e promove qualquer conta ChatGPT retornada a CONNECTED, limpando o pendingLoginId. O teste de revisão simulou uma tentativa nova pendente com uma conta anterior em cache: o serviço a concluiu indevidamente. Falha/cancelamento da tentativa atual também não são consumidos pelo caminho que atende a UI.

Correção: integrar conclusão correlacionada por loginId à máquina de estados, impedir eventos/respostas antigos de sobrescrever a tentativa atual e só confirmar conta após o sucesso da tentativa correta. Documentar leitura de sessão em cache versus verificação/renovação atual. [Contrato oficial de login](https://developers.openai.com/codex/app-server).

### 6. P2 — Teste de interface excluído do CI

Arquivo: `vitest.config.ts`, linha 12; teste novo `tests/providers/openai-connection-card.test.tsx`.

O include é `tests/**/*.test.ts`, excluindo `.test.tsx`. Portanto o run verde não comprova os testes de interface descritos no relatório. O teste existente usa SSR/string, não interação de DOM nem callbacks do ConnectionManager.

Correção: incluir TSX e configurar transformação JSX compatível com a versão instalada; adicionar testes de interação que cubram iniciar, status, cancelar, erro, refresh e reconectar. Atualizar a documentação com a evidência realmente executada.
